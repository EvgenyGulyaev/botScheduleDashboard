# Google Drive для wedding-en.ru

Гости загружают оригиналы и смотрят галерею через API сайта. Их Google-аккаунты не нужны. Drive-папка остаётся закрытой; API получает доступ по `drive.file` только к созданным приложением файлам. Публичных OAuth-маршрутов нет.

## Что требуется от владельца

1. В [Google Cloud Console](https://console.cloud.google.com/) создать отдельный проект и включить **Google Drive API**.
2. В **Google Auth Platform** заполнить Branding/Audience: External, указать название приложения и свою почту. Для первоначальной проверки добавить свою Google-почту в Test users.
3. В Data Access добавить scope `https://www.googleapis.com/auth/drive.file`.
4. В Clients создать OAuth client с типом **Desktop app**, скачать JSON на свой компьютер. Desktop client использует loopback `http://127.0.0.1:<случайный порт>/callback`; отдельный HTTPS redirect сайта не нужен.
5. До постоянной эксплуатации перевести External consent screen в **In production**. В Testing refresh token для Drive обычно истекает через 7 дней. После перевода в production авторизовать аккаунт заново. При требованиях Google к публикации завершить предложенные Google шаги; доступность квот и длительность токенов определяет Google.

Пароль Google, коды 2FA, содержимое client JSON и refresh token в чат не отправлять. Разработчику достаточно подтвердить готовность OAuth-проекта; сам JSON нужен только локальной команде.

## Однократное подключение на компьютере владельца

Создать защищённый каталог вне репозитория, затем запустить из backend-репозитория:

```sh
rtk proxy mkdir -p "$HOME/.config/wedding"
rtk proxy chmod 700 "$HOME/.config/wedding"
rtk proxy go run ./cmd/wedding-drive-auth \
  -client "$HOME/Downloads/client_secret_GOOGLE_CLIENT.json" \
  -out "$HOME/.config/wedding/wedding-drive.json" \
  -origin https://wedding-en.ru \
  -folder 'Свадебные фото и видео'
```

Открыть напечатанную Google-ссылку **на этом же компьютере**, войти в свой личный Google-аккаунт и разрешить доступ. Команда проверяет state и PKCE, получает offline refresh token, создаёт новую закрытую папку и атомарно пишет JSON с правами `0600`. Секреты не печатаются. Ожидание авторизации ограничено 10 минутами.

Команда не перезаписывает существующий файл. Для повторной авторизации использовать новый защищённый путь, затем заменить серверный конфиг. Повторная команда создаёт новую папку; старые файлы остаются в прежней папке. Если папку нужно сохранить при переподключении, администратор локально переносит прежний `folder_id` в новый защищённый конфиг; OAuth client/project должны оставаться теми же. Сохранить прежний `cookie_key`, если требуется оставить гостевые сессии. Не показывать эти конфиги в чате или логах.

Ссылки на произвольную существующую папку недостаточно для scope `drive.file`: здесь используется папка, созданная этим приложением. Google Picker для выбора другой папки в первой версии отсутствует.

## Сервер

Безопасно передать JSON по SSH/SFTP в закрытый каталог, принадлежащий пользователю backend. Каталог должен быть `0700`, JSON — `0600`. Значения окружения процесса:

```text
WEDDING_DRIVE_CONFIG=/var/lib/bot-dashboard/wedding/wedding-drive.json
WEDDING_MEDIA_ORIGIN=https://wedding-en.ru
```

`WEDDING_MEDIA_ORIGIN` совпадает с публичным origin **без `/` в конце**. Оно переопределяет `origin` в конфиге. `https://www.wedding-en.ru` следует перенаправлять на канонический домен до приложения.

Процесс должен иметь право атомарно заменять JSON в его каталоге: обновлённый refresh token сохраняется туда с `0600`. Рядом создаётся `wedding-drive.json.sessions.db` (`0600`), содержащая resumable URL и состояние загрузок. Этот файл тоже секретный; не публиковать и не копировать в репозиторий. Конфиг и БД должны лежать на постоянном диске. Для смены конфигурации нужен перезапуск API. При неверных правах или повреждённой конфигурации медиа выключается; остальные свадебные маршруты продолжают работать.

Для видео, несовместимых с аппаратным декодером Apple, можно подготовить отдельный MP4 для просмотра (H.264 Main, yuv420p, AAC, faststart). Конвертацию выполняют локально; готовый файл сохраняют в отдельной приватной папке Google Drive, вне общего альбома. В защищённом JSON необязательное поле `video_previews` сопоставляет ID оригинала и ID версии для просмотра: `{"ORIGINAL_DRIVE_ID":"PREVIEW_DRIVE_ID"}`. После перезапуска API обычный `/media/ID/content` передаёт совместимую версию с поддержкой Range, а `?download=1` сохраняет оригинал. Доступ сначала проверяется по оригиналу в папке альбома. Копия не добавляется в список и счётчик галереи, не хранится на VPS. Автоматическое преобразование новых загрузок этим параметром не включается.

API не создаёт папку и не даёт публичный доступ при старте. При отсутствии конфига status возвращает `connected:false`. Гостевое подтверждение кода продолжает работать; до подключения Drive его cookie подписывается временным ключом и сбрасывается при перезапуске процесса.

### Автоматическая подготовка новых видео

После установки `ffmpeg`/`ffprobe` (libx264, AAC, zscale, tonemap) добавить в защищённый JSON:

```json
"video_processing": {
  "enabled": true,
  "folder_id": "PRIVATE_PREVIEW_FOLDER_ID",
  "work_dir": "/var/lib/bot-dashboard/wedding/video-work"
}
```

Папка превью должна быть приватной и отличаться от папки общего альбома. Конфиг сохраняет права `0600`; рабочие каталоги — `0700`. Пути инструментов по умолчанию `/usr/bin/ffmpeg`, `/usr/bin/ffprobe`, `/usr/bin/systemd-run`, `/usr/bin/systemctl`; API должен иметь право запускать transient systemd units. Изменения nginx для обработки не требуются.

Завершённая загрузка видео атомарно добавляет задачу в существующую Bolt БД. Один worker запускается вместе с API и восстанавливает прерванные задачи после перезапуска. Ошибки повторяются через 1 и 5 минут, максимум три попытки; нехватка места и штатное завершение не расходуют попытку. Готовые копии находятся по тегам Drive и повторно используются после сбоя. Старые видео автоматически не перекодируются; ручные `video_previews` сохраняют приоритет.

Для кодирования и проверки файла действуют CPUQuota=50%, MemoryMax=192M, MemorySwapMax=128M, Nice=15, TasksMax=32. Кодирование ограничено четырьмя часами, probe — 30 секундами. Просмотр: MP4 faststart, H.264 Main 3.1, до 1280 по длинной и 720 по короткой стороне, до 30 fps, AAC-LC stereo 128k/48k; HDR преобразуется в SDR. Исходник временно скачивается двумя потоками по 8 МиБ. На диске резервируется исходник + максимум 512 МиБ результата + 1 ГиБ свободного места. После завершения временные файлы удаляются; оригиналы на Drive не меняются.

Поле `preview_status` у видео: `queued`, `processing`, `ready`, `failed`; отсутствие поля сохраняет прежний просмотр. Пока копия готовится, плеер не загружает оригинал; скачать оригинал можно сразу. `GET /wedding/media/previews?ids=ID1,ID2` возвращает `{"statuses":{"ID1":"processing"}}`: до 40 ID, одна локальная транзакция без запросов Drive и без занятия слота медиапотока. Нужна действующая гостевая авторизация. Галерея опрашивает текущую страницу и открытый ролик одним запросом раз в 5 секунд; при закрытии/скрытии вкладки опрос прекращается. Готовая копия подключается автоматически.

Проверка production 19.10.2026: автоматическая обработка включена, nginx не менялся. Тестовый HEVC Main10 4K PQ (0,5 секунды) загрузился через гостевой API за 2,2 секунды, прошёл `queued → processing → ready`; копия H.264 Main 3.1 1280×720 открылась в Chrome и WebKit. Скачать оригинал удалось без изменения SHA-256; Range вернул `206`, копия находилась в отдельной приватной папке. Тестовые оригиналы и копии перемещены в корзину, рабочий каталог пуст. Отдельные PQ/HLG проверки под реальными cgroup-лимитами прошли; 4K достигал 192 МиБ памяти и около 124 МиБ swap, поэтому большие 4K могут готовиться долго или не уложиться в лимит ресурсов. Эти короткие fixtures проверяют совместимость, а не скорость обработки длинных роликов.

Сначала развернуть API и nginx, затем frontend. Проверить `/api/wedding/media/status` в браузере. При включённом коде пройти гостевую проверку ещё раз: старого localStorage недостаточно.

## Контракт галереи

- `GET /wedding/media/ID/preview` передаёт готовое изображение Drive до 1600 px для просмотра фото. Исходный файл не изменяется, отдельные копии на VPS не создаются. Проверка гостевой cookie и принадлежности оригинала папке альбома выполняется перед каждым ответом, включая попадание в кеш. Временный URL Google клиенту не возвращается. Если Drive не дал поддерживаемое превью, маршрут возвращает ошибку; миниатюра и скачивание оригинала остаются доступны.
- Обычный просмотр и фоновая предзагрузка используют `/preview`; оригинал `/content` запрашивается при увеличении или по ссылке скачивания `?download=1`. Для фото без миниатюры возможен прежний просмотр оригинала. HEIC/HEIF/TIFF показываются через совместимое превью.
- Малые миниатюры и крупные превью имеют разные ключи в общем кеше: максимум 64 записи и 8 МиБ, TTL одна минута. При заполнении удаляются просроченные и наименее недавно использованные записи по одной. Изображения крупнее лимита отдельной записи передаются без сохранения в этом кеше. Кеш не заменяет проверку прав доступа.

- `GET /wedding/media?cursor=<next_cursor>` возвращает `{ "items": [...], "next_cursor": "..." }`. Пустой `next_cursor` завершает список. API запрашивает у Drive до 20 разрешённых фото/видео за страницу, в порядке `createdTime desc`; неподдерживаемые типы и папки исключаются Google-запросом. Drive может вернуть короткую или пустую промежуточную страницу: продолжать следует по `next_cursor`, а не по числу `items`.
- `GET /wedding/media/summary` возвращает `{ "total": 123 }`: точное количество разрешённых фото/видео, доступных приложению в настроенной закрытой папке, без удалённых файлов. Summary читает только метаданные страницами до 1000 файлов; оригиналы и превью не скачиваются. Summary запрашивается независимо от списка и открытия выбранного медиа.
- Оба маршрута используют действующую гостевую проверку; при включённом коде без актуальной cookie возвращается `401`. Через nginx публичный префикс — `/api/wedding/media`.
- Summary кешируется на 30 секунд, включая нулевой результат. Параллельные запросы делят один выполняющийся подсчёт. Только сам подсчёт занимает один из восьми общих медиа-слотов; чтение кеша и ожидание подсчёта не блокируют просмотр фото и загрузки. Завершение загрузки сбрасывает список и summary; результат начатого до сброса запроса не сохраняется в кеш. Внешние изменения папки отражаются после истечения кеша.
- При неполном поиске Drive, повторном/слишком длинном токене или превышении 10 000 страниц summary возвращает `503` без частичного `total`. Общий таймаут медиа-запроса — 3 минуты; ошибки Drive и квот сохраняют обычную обработку API. Подсчёт не гарантирует снимок при одновременных внешних изменениях папки.

## nginx

В существующем HTTPS virtual host добавить более специфичный location перед общим API. Порт backend взять из действующей конфигурации; `BACKEND_PORT` ниже — обозначение, а не готовое значение:

```nginx
location ^~ /api/wedding/media {
    # /api/wedding/media/... -> /wedding/media/...
    proxy_pass http://127.0.0.1:BACKEND_PORT/wedding/media;
    proxy_http_version 1.1;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
    proxy_set_header Range $http_range;
    proxy_set_header If-Range $http_if_range;
    proxy_set_header Connection "";
    client_max_body_size 9m;
    client_body_timeout 180s;
    proxy_request_buffering off;
    proxy_buffering off;
    proxy_cache off;
    proxy_read_timeout 190s;
    proxy_send_timeout 190s;
}
```

Общий `/api/` location также должен передавать `Host` и `X-Forwarded-Proto` для `/wedding/access/verify`; не удалять `Origin`, `Cookie` и `Set-Cookie`. API слушает только приватный/loopback интерфейс за HTTPS proxy. Silverlining доверяет `X-Forwarded-Proto` только от loopback; рекомендуемая схема nginx → `127.0.0.1` → Go. Сам API проверяет mutation `Origin`; CORS для внешнего frontend не требуется.

Проверить nginx штатным `nginx -t`, перезагрузить его только после проверки реальной конфигурации. Не подменять существующие TLS/доменные настройки приведённым фрагментом.

## Проверка с подключённым Google

- На телефоне выбрать JPEG/HEIC и видео, дождаться завершения; проверить оригиналы в закрытой Drive-папке.
- Открыть галерею на другом телефоне; фото, видео, перемотка и скачивание оригинала должны работать.
- Прервать сеть во время загрузки, вернуть её и нажать повтор: статус определяет принятые Drive байты; завершённый файл повторно не отправляется.
- При включённом коде проверить анонимный список (`401`), успешный код и повторную блокировку после изменения кода.
- Убедиться, что произвольный ID файла вне свадебной папки возвращает `404`.

Без действий владельца этот сценарий с настоящим Drive не проверен; локальные тесты используют поддельный Google HTTP API.

## Границы первой версии

- Один файл — максимум 1 ГиБ, часть — максимум 8 МиБ. Не последняя часть кратна 256 КиБ. На сервере хранится максимум одна часть на активную загрузку, а не весь файл. Одновременно разрешено 8 медиа-запросов; остальные получают `429`.
- Создание сессий: максимум 60 в минуту на процесс, 100 за 24 часа на гостевую cookie и 2048 всего за 24 часа. Сессии завершённых загрузок сохраняются для идемпотентного повтора; просроченные записи удаляются при следующем создании/сохранении. Ограничения оперативного счётчика сбрасываются при перезапуске; БД сессий сохраняется.
- Фото: JPEG, PNG, GIF, WebP, BMP, TIFF, HEIC/HEIF, AVIF. Видео: MP4/M4V, MOV/QuickTime, WebM, 3GP/3G2, MPEG, AVI, Matroska. Тип сверяется с сигнатурой первой части; SVG и исполняемые файлы не принимаются. Это проверка формата, не антивирусная проверка и не перекодирование.
- Загрузка продолжает работу в открытой странице. API сохраняет сессию после перезапуска, но интерфейс не восстанавливает выбор файлов после закрытия вкладки. Срок локальной сессии — 24 часа; Google может завершить свою сессию раньше.
- HEIC/HEIF/TIFF и видеокодеки воспроизводятся не во всех браузерах. Для фото используется доступное превью Drive, для оригиналов доступно скачивание. Автоматическое перекодирование отсутствует.
- Все просмотры/скачивания идут через VPS. Google Drive применяет API/download/storage quotas; ошибки квот возвращают `429` или `503` с понятным сообщением. Это галерея одной свадьбы, не неограниченный видеохостинг.
- Контент передаётся потоково с поддержкой одного HTTP byte Range. Silverlining не предоставляет request context отмены по disconnect: разрыв загрузки/чтения заканчивает передачу при ошибке I/O, upstream дополнительно ограничен 3 минутами. Для длинного медленного видео это может потребовать повторного Range-запроса браузера.
- Приватные браузерные ответы имеют `Cache-Control: private, no-store`. Внутренний серверный кеш ограничен 32 страницами списка на 10 секунд, одним summary на 30 секунд и 16 превью до 512 КиБ каждое на 60 секунд; заполненный кеш страниц/превью сбрасывается. Завершение загрузки инвалидирует список и summary, включая параллельные устаревшие запросы. Гостевой доступ проверяется до кеша; перед каждым превью, включая кешированное, заново проверяется принадлежность файла папке через Drive. Список загружается страницами до 20 медиа.
- Переходы Google HTTP redirect не выполняются; thumbnail URL разрешены только HTTPS на `*.googleusercontent.com`. Если реальный Google начнёт требовать другой доверенный хост/redirect, он должен быть явно проверен и добавлен; произвольные адреса backend не открывает.

Документация Google: [Desktop OAuth](https://developers.google.com/identity/protocols/oauth2/native-app), [resumable uploads](https://developers.google.com/workspace/drive/api/guides/manage-uploads), [downloads and Range](https://developers.google.com/workspace/drive/api/guides/manage-downloads).
